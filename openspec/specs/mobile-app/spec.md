# Mobile App Specification

## Purpose
Определяет поведение мобильного клиента CityQuest (iOS/Android) на Flutter: аутентификация и сессия на устройстве, каталог и геопоиск квестов, деталь и лайки, движок прохождения с геочекпоинтами, профиль и история, а также требования надёжности (кеш, оффлайн-обработка, системные пермишены).

## Requirements

### Requirement: R01 — Установка и конфигурация платформы
Мобильное приложение ДОЛЖНО быть собрано из единой Flutter-кодовой базы для iOS и Android и ДОЛЖНО идентифицировать себя в API через заголовок `X-App-Platform` (формат `ios/<версия>` / `android/<версия>`).

#### Scenario: S01 — Запуск на обеих платформах
- **WHEN** приложение запускается на iOS (Simulator/устройство) и Android (APK)
- **THEN** пользователь видит стартовый экран и приложение выполняет запросы к API корректно

#### Scenario: S02 — Заголовок платформы во всех запросах
- **WHEN** приложение выполняет любой запрос к API
- **THEN** запрос содержит заголовок `X-App-Platform` с корректным форматом `ios/<version>` или `android/<version>`

### Requirement: R02 — Аутентификация и сессия на устройстве
Приложение ДОЛЖНО поддерживать регистрацию и вход (username+password) через существующий механизм JWT HttpOnly cookies, ДОЛЖНО сохранять сессию между перезапусками и корректно завершать сессию. Если платформа/ОС блокирует cookies, приложение ДОЛЖНО переходить на fallback — заголовок `Authorization: Bearer <token>` из тела ответа.

#### Scenario: S03 — Регистрация
- **WHEN** пользователь вводит валидные email, username, password и подтверждает регистрацию
- **THEN** приложение создаёт аккаунт и автоматически выполняет вход
- **AND** при неудаче (занятый email/username, невалидные данные) показывает понятное сообщение об ошибке

#### Scenario: S04 — Вход и восстановление сессии
- **WHEN** пользователь выполняет вход или повторно открывает приложение
- **THEN** приложение восстанавливает сессию (проверка через `GET /api/auth/me`)
- **AND** при невалидной сессии автоматически показывает экран входа

#### Scenario: S05 — Выход
- **WHEN** пользователь выходит из аккаунта
- **THEN** cookie/токен очищаются и все ресурсы переходят в гостевой режим

### Requirement: R03 — Каталог квестов и геопоиск
Приложение ДОЛЖНО предоставлять список квестов с фильтрами (город, сложность, популярные), детальной карточкой, а также поиск квестов рядом через `GET /api/quests/nearby` с координатами устройства.

#### Scenario: S06 — Список квестов с фильтрами
- **WHEN** пользователь открывает каталог
- **THEN** приложение загружает список квестов с пагинацией
- **AND** фильтры по городу/сложности/популярности корректно применяются

#### Scenario: S07 — Города с кешем
- **WHEN** приложение запрашивает справочник городов
- **THEN** данные кешируются локально с TTL 1 час (как в веб-клиенте)
- **AND** при отсутствии сети используется кешированная версия

#### Scenario: S08 — Квесты рядом
- **WHEN** пользователь запрашивает квесты поблизости
- **THEN** приложение запрашивает георазрешения и отправляет координаты на `GET /api/quests/nearby`
- **AND** результаты отсортированы по удаленности
- **AND** при отказе в георазрешении приложение корректно объясняет, как включить геолокацию

### Requirement: R04 — Деталь квеста и лайки
Приложение ДОЛЖНО показывать детальную информацию квеста и позволять авторизованным пользователям ставить/убирать лайки с оптимистичным обновлением UI.

#### Scenario: S09 — Деталь квеста
- **WHEN** пользователь открывает квест
- **THEN** отображаются описание, автор, сложность, длительность, дистанция, стартовые координаты и статус лайка (если авторизован)

#### Scenario: S10 — Оптимистичный лайк
- **WHEN** авторизованный пользователь переключает лайк
- **THEN** UI мгновенно обновляется, а запрос выполняется в фоне
- **AND** при ошибке сети состояние откатывается с уведомлением

### Requirement: R05 — Движок прохождения с геочекпоинтами
Приложение ДОЛЖНО позволять начинать, ставить на паузу, возобновлять, отменять и завершать квесты, а также проверять геопозицию на текущем шаге через `POST /api/user/progress/{questId}/check` с отображением карты маршрута.

#### Scenario: S11 — Старт квеста
- **WHEN** авторизованный пользователь начинает новый квест
- **THEN** приложение создаёт активный прогресс и показывает первый чекпоинт на карте
- **AND** при наличии другого активного квеста приложение предлагает выбор (возобновить/отменить предыдущий)

#### Scenario: S12 — Проверка чекпоинта по GPS
- **WHEN** пользователь приближается к чекпоинту в пределах радиуса
- **THEN** приложение отправляет координаты, получает `success: true` и плавно переводит к следующему шагу
- **AND** если пользователь вне радиуса, приложение показывает дистанцию до точки и подсказку направления

#### Scenario: S13 — Пауза/возобновление/отмена
- **WHEN** пользователь ставит квест на паузу, возобновляет или отменяет его
- **THEN** приложение корректно синхронизирует статус с backend
- **AND** при потере сети сохраняет локальное состояние для повторной синхронизации

#### Scenario: S14 — Автозавершение последнего шага
- **WHEN** пользователь успешно проходит последний чекпоинт
- **THEN** приложение отображает экран завершения с поздравлением и статистикой

#### Scenario: S15 — Обработка георазрешений
- **WHEN** приложение запрашивает геолокацию во время прохождения
- **THEN** запрашивает точное разрешение (`ACCESS_FINE_LOCATION` / `WhenInUse`) и работает с `LocationAccuracy.high`
- **AND** при постоянном отказе корректно перенаправляет в настройки ОС

### Requirement: R06 — Профиль и история
Приложение ДОЛЖНО отображать профиль пользователя и его историю прохождений (активные, на паузе, завершённые) с возможностью возобновления активного квеста.

#### Scenario: S16 — Профиль
- **WHEN** пользователь открывает профиль
- **THEN** отображаются username, email, дата регистрации и сводка достижений

#### Scenario: S17 — История и возобновление
- **WHEN** пользователь просматривает историю
- **THEN** приложение показывает группы квестов по статусам
- **AND** позволяет продолжить активный/приостановленный квест с текущего шага

### Requirement: R07 — Надёжность и оффлайн-поведение
Приложение ДОЛЖНО корректно обрабатывать отсутствие сети, ошибки API и системные разрешения, не допуская потери данных пользователя.

#### Scenario: S18 — Обработка ошибок сети
- **WHEN** запрос к API завершается ошибкой сети/таймаутом/5xx
- **THEN** приложение показывает уведомление и предложение повторить
- **AND** не теряет локальное состояние (активный квест, кеш)

#### Scenario: S19 — Единый формат ошибок
- **WHEN** API возвращает ошибку 400/401/403/404/409/422
- **THEN** приложение «переводит» её в читаемое сообщение на русском языке
- **AND** для 401 выполняет автоматический переход в гостевой режим

### Requirement: Экран прохождения квеста
Мобильное приложение ДОЛЖНО предоставлять специальный UI-экран для активного прохождения квеста, отображающий текущий этап, задачу и элементы управления.

#### Scenario: Отображение базовой информации
- **WHEN** пользователь находится на экране прохождения квеста
- **THEN** приложение отображает: название квеста, номер текущего этапа и общее количество этапов, медиаконтент задачи (фото/текст/видео/аудио), кнопку "Проверить" ("Я на месте"), сворачиваемый список шагов и кнопку паузы.

### Requirement: Сворачиваемый список шагов
Приложение ДОЛЖНО отображать сворачиваемый список всех шагов квеста, скрывая детали будущих шагов для квестов линейного типа.

#### Scenario: Просмотр списка шагов (линейный квест)
- **WHEN** пользователь разворачивает список шагов в линейном квесте
- **THEN** пройденные шаги подсвечиваются ярким цветом и содержат полные данные, текущий шаг выделен, а все будущие шаги отображаются как неизвестные (скрыты детали).

### Requirement: Проверка геопозиции (бесконечные попытки)
Приложение ДОЛЖНО позволять пользователю неограниченное число раз проверять свою геопозицию ("Я на месте") для текущего шага.

#### Scenario: Успешная проверка локации
- **WHEN** пользователь нажимает кнопку "Я на месте" и его координаты находятся в радиусе чекпоинта
- **THEN** приложение отправляет запрос на сервер, получает подтверждение, показывает сообщение об успехе и переводит квест на следующий шаг (или завершает, если шаг последний).
- **TESTS**:
  - Backend: [UserProgressControllerTest::testCheckStepWorksCorrectly](../../../../backend/tests/UserProgress/Presentation/Controller/UserProgressControllerTest.php)

#### Scenario: Неудачная проверка локации (бесконечные попытки)
- **WHEN** пользователь нажимает кнопку "Я на месте", но его координаты вне радиуса чекпоинта
- **THEN** приложение отправляет запрос на сервер, получает отказ, показывает сообщение о неудаче (или оставшееся расстояние) и оставляет пользователя на текущем шаге, позволяя пробовать снова.
- **TESTS**:
  - Backend: [UserProgressControllerTest::testCheckStepWorksCorrectly](../../../../backend/tests/UserProgress/Presentation/Controller/UserProgressControllerTest.php)

### Requirement: Пауза квеста
Приложение ДОЛЖНО позволять поставить активный квест на паузу прямо с экрана прохождения.

#### Scenario: Постановка на паузу
- **WHEN** пользователь нажимает кнопку "Поставить на паузу"
- **THEN** приложение отправляет запрос на сервер, меняет статус квеста и перенаправляет пользователя на экран деталей квеста или главный экран.

## Non-Goals
- Полный оффлайн-режим (только тёплый кеш) в текущей итерации.
- Push-уведомления, оплаты, соцвходы.
- WebView-обёртки: только нативный Flutter.
