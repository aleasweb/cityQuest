## Context

См. `proposal.md` — Why. Профиль уже получает `activeQuest` и `pausedQuests` из существующего API истории. На главном экране карточка активного квеста живёт в дизайн-системе как глупый виджет и берёт данные сверху. В профиле те же данные рисуются локальными карточками другого вида; возобновление и отказ для паузы из профиля не вызываются, хотя `ProgressRepository.start` и `abandon` уже есть.

## Goals / Non-Goals

**Goals:**
- Собрать секции профиля из виджетов дизайн-системы, а не из локальных карточек.
- Оставить `ActiveQuestBlock` глупым; пустой текст рендерит экран профиля.
- Добавить соседний глупый виджет карточки на паузе с теми же токенами и слотами действий.
- Возобновление и отказ идут через существующий progress API; после успеха обновляются профиль и список прогресса.

**Non-Goals:**
- Новый bounded context или правки Event Sourcing на backend: `QuestResumedEvent` / `QuestAbandonedEvent` уже пишутся текущими эндпоинтами.
- Обобщать активную карточку в один виджет с вариантами.
- Менять контракт `ActiveQuestBlock` ради пустого состояния.

## Decisions

### 1. Переиспользовать `ActiveQuestBlock` как есть
- **Решение:** Профиль передаёт в существующий виджет название, шаг, изображение и `onTap` на маршрут прохождения. Текст «Нет активных квестов» — ветка экрана, не виджета.
- **Обоснование:** На каталоге пустое состояние — скрыть блок. В профиле — показать текст. Логика хозяина не должна протекать в дизайн-систему.
- **Альтернатива:** Научить виджет режиму empty. Отклонено: сломает каталог или добавит лишний API.

### 2. Отдельный `PausedQuestBlock`, а не вариант активной карточки
- **Решение:** Новый stateless-виджет в `mobile/lib/app/core/design_system/widgets/`. Та же сетка, тени, токены `AppSpacing` / `AppColors` / `AppTextStyles`. Коллбэки `onContinue?` и `onAbandon`. Кнопка «Продолжить» рендерится только если `onContinue != null`.
- **Обоснование:** Визуально близко, набор действий другой. Два глупых виджета проще тестировать, чем флаги варианта.
- **Альтернатива:** Один виджет с `enum variant`. Отклонено: усложняет активную карточку ради одного экрана.

### 3. Действия паузы на уровне профиля
- **Решение:** «Продолжить» вызывает `ProgressRepository.start(questId)` (существующее возобновление), затем переход на экран прохождения и invalidate профиля / списка прогресса. «Отказаться» сначала показывает диалог подтверждения, затем `abandon(questId)` и обновляет те же провайдеры. `onContinue` передаётся только если `profile.activeQuest == null`.
- **Обоснование:** Backend уже запрещает второй активный квест (409). Скрытая кнопка не даёт упереться в конфликт. Диалог нужен: отказ необратим.
- **Альтернатива:** Диалог «поставить активный на паузу и продолжить этот». Отклонено: пользователь явно просил «Продолжить» только без активного квеста.

### 4. Слои и изоляция фич
- **Решение:** Виджеты остаются в `core/design_system`. Профиль вызывает `progressRepositoryProvider` (или тонкий метод в `ProfileController`), не импортируя `presentation`/`data` прогресса.
- **Обоснование:** Совпадает с правилом изоляции feature-first из `openspec/specs/mobile-app/architecture.md`.

## Risks / Trade-offs

- **[Риск]** После отказа/возобновления статистика и карточки останутся старыми.
  → **Смягчение:** после успеха invalidate `profileControllerProvider` и `progressListControllerProvider`.
- **[Риск]** 409 при гонке (активный квест появился на другом устройстве).
  → **Смягчение:** показать ошибку API и обновить профиль; кнопку «Продолжить» после refresh скрыть.
- **[Компромисс]** Два похожих виджета вместо одного.
  → Принимаем ради простого API активной карточки.

## Migration Plan

Только клиентское обновление Flutter. Откат — вернуть локальные карточки профиля. Backend и данные не меняются.
