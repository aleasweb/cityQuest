## Context

В рамках мобильного приложения CityQuest (Flutter) разрабатывается главный экран (каталог квестов). Для обеспечения удобного UX пользователю, имеющему активный квест (находящемуся в процессе прохождения), необходимо быстро возвращаться к нему без необходимости поиска.
См. `proposal.md` для деталей мотивации и требований. Архитектура Flutter-приложения использует Feature-First подход и Riverpod для стейт-менеджмента.

## Goals / Non-Goals

**Goals:**
- Создать изолированный, переиспользуемый UI-компонент `ActiveQuestBlock` в дизайн-системе мобильного приложения (`lib/app/core/design_system`).
- Интегрировать компонент на главный экран мобильного приложения.
- Использовать существующий стейт (`UserProgress` provider) для получения данных о статусе.

**Non-Goals:**
- Изменения в Backend API.
- Изменения в Web frontend приложении.
- Создание новой бизнес-логики для квестов — используем существующие API и стейт.

## Decisions

### 1. Расположение UI-компонента
- **Решение:** Разместить `ActiveQuestBlock` в `lib/app/core/design_system/widgets/` (или аналогичной директории общих компонентов).
- **Обоснование:** Блок может потребоваться на других экранах в будущем (например, профиль, экран карты). Вынесение его в общие виджеты позволяет избежать дублирования кода.
- **Альтернативы:** Разместить только внутри фичи `quest_catalog` (главного экрана). Отклонено, так как нарушает переиспользуемость.

### 2. Управление состоянием внутри компонента
- **Решение:** Компонент `ActiveQuestBlock` должен быть "глупым" (stateless widget), получающим данные (название квеста, прогресс) через конструктор, или "умным" (ConsumerWidget), подписывающимся на Riverpod-провайдер глобального прогресса.
Выбран подход **StatelessWidget** (глупый компонент).
- **Обоснование:** Это улучшает тестируемость и переиспользуемость компонента в Storybook/Design System. Интеграция с Riverpod будет происходить на уровне родительского виджета (экрана каталога).
- **Альтернативы:** Сделать виджет жестко привязанным к Riverpod. Отклонено, так как снижает гибкость использования компонента в изоляции.

### 3. Обработка навигации
- **Решение:** Компонент будет принимать коллбэк `VoidCallback onTap`, который родительский виджет реализует с помощью `context.go('/quest_process/:id')` (или аналогичного роута go_router).
- **Обоснование:** Разделение ответственности: компонент отвечает только за рендеринг, а родительский фича-виджет — за навигацию.

## Risks / Trade-offs

- **[Риск]** Отсутствие данных прогресса при первой загрузке экрана.
  → **Смягчение**: Если данные еще грузятся, блок можно не показывать или показывать скелетон. Так как требование — показывать *только если есть активный квест*, в случае `null` или загрузки возвращается пустой виджет (`SizedBox.shrink()`), чтобы не дергать UI.
- **[Риск]** Рассинхронизация локального кеша и сервера.
  → **Смягчение**: При возобновлении приложения (lifecycle state resumed) необходимо рефрешить состояние прогресса на уровне глобального провайдера.
