## Context

Backend уже предоставляет готовое API для прохождения квестов (Event Sourcing в `UserProgress`, эндпоинты геочекпоинтов `POST /api/user/progress/{questId}/check`, старт, пауза). Основная задача — реализовать UI и клиентскую логику на Flutter. 
Приложение использует Riverpod для State Management, go_router для навигации, Dio для сети.
Архитектура: Feature-First (в `lib/app/features/`).

## Goals / Non-Goals

**Goals:**
- Создать feature-модуль `quest_process` в мобильном приложении.
- Реализовать `QuestProcessStateNotifier` (или AsyncNotifier) для управления локальным состоянием прохождения.
- Обеспечить интеграцию с геолокацией устройства (получение координат по запросу пользователя при проверке).
- Сверстать UI согласно предоставленному макету (со сворачиваемым списком шагов, отображением задачи и кнопкой проверки).

**Non-Goals:**
- Фоновое (background) отслеживание геолокации без участия пользователя (сейчас пользователь сам жмет кнопку проверки).
- Реализация веб-версии этого функционала.
- Изменение backend API.

## Decisions

### 1. Архитектура Feature-модуля (quest_process)
Модуль будет располагаться в `lib/app/features/quest_process/` и следовать слоистой архитектуре:
- `data/`: `QuestProcessRepository` (вызовы API для проверки чекпоинтов, получения данных квеста).
- `domain/`: модели `QuestProgress`, `QuestStep` (переиспользование или создание специализированных DTO для UI).
- `application/`: `QuestProcessController` (Riverpod AsyncNotifier), который хранит состояние (`quest`, список `steps`, `currentStepIndex`, статус загрузки/ошибки).
- `presentation/`: `QuestProcessScreen` и виджеты (карточка текущего этапа, список шагов).

*Alternative:* Реализовать все в рамках существующей фичи `quest_details`.
*Rationale:* Процесс прохождения имеет сложный стейт (геолокация, проверка, анимации списка), поэтому логично вынести его в отдельный контроллер и экран, чтобы не перегружать детали квеста.

### 2. Управление состоянием (Riverpod)
`QuestProcessController` будет управлять:
- Загрузкой квеста и его шагов.
- Локальным счетчиком текущего шага (`currentStepIndex`).
- Обработкой нажатия "Я на месте": 
  1. Запрос геолокации (через пакет `geolocator`).
  2. Вызов `POST /api/user/progress/{questId}/check`.
  3. В случае успеха: инкремент `currentStepIndex` или завершение квеста.
  4. В случае неудачи: отображение ошибки без смены шага (бесконечные попытки).

### 3. Локация
Использовать пакет `geolocator`. Проверка происходит только "по требованию" (кнопка "Я на месте").
- *Rationale:* Экономит батарею, проще в реализации, чем фоновый трекинг.

### 4. UI: Список шагов
Будет использован `SliverList` или кастомный виджет с анимацией для отображения списка шагов. Шаги до `currentStepIndex` отображаются с деталями (яркие), шаг на `currentStepIndex` — активен, шаги после `currentStepIndex` — заблюрены/с надписью "Неизвестный этап".

## Risks / Trade-offs

- [Risk] Нет доступа к геолокации (пользователь запретил).
  → *Mitigation:* При нажатии "Я на месте" явно проверять разрешения и, если нет, показывать диалог с просьбой перейти в настройки.
- [Risk] Потеря сети при прохождении.
  → *Mitigation:* Запрос на чекпоинт просто вернет ошибку сети, стейт не изменится. Пользователь сможет повторить попытку. (Полноценный оффлайн режим — Non-Goal).

## Testing (Backend Simulation)

Для проверки корректности API в контексте мобильного прохождения квеста (сохранение состояния в Event Sourcing, смена статусов, бесконечные проверки) будет добавлен интеграционный тест на backend (PHPUnit). Это позволит гарантировать, что текущее API полностью поддерживает ожидаемое поведение клиента без сюрпризов во время мобильной разработки.
